# Windlass

A small notification manager: Spring Boot REST API, PostgreSQL persistence, and a responsive vanilla JavaScript UI. No separate frontend build is needed.

Detailed feature, API, persistence, deployment, and code documentation is in
[docs/README.md](docs/README.md), with an index for AI agents.

## Run

Requires JDK 24 or newer and a PostgreSQL database. The Maven wrapper downloads Maven and dependencies on first use.

```sh
./mvnw spring-boot:run
```

Open http://localhost:8080. Create notifications, search by title/description/source, inspect metadata, edit, mark as seen, and delete from the UI. Unread cards are highlighted and the header shows the unread count.

Flyway applies versioned database migrations automatically on startup, including upgrades of existing databases. See [Database migrations](docs/migrations.md) for adding schema changes.

Set `DATABASE_URL` to a PostgreSQL JDBC URL and set `DATABASE_USERNAME` and
`DATABASE_PASSWORD` for the database account. See the
[deployment guide](docs/deployment.md#configuration) for setup. Set `SERVER_PORT`
to change the port. The app is intended for local use and has no authentication.

## Model

| Field | Type | Behavior |
| --- | --- | --- |
| `id` | UUID string | Generated by the server; immutable |
| `title` | string | Required, nonblank, up to 200 characters |
| `description` | string | Optional, up to 10,000 characters; defaults to empty |
| `notification_source` | string | Required, nonblank, up to 200 characters |
| `received_on` | ISO 8601 timestamp | Defaults to now on creation; retained on update if omitted |
| `unread` | boolean | Defaults to `true`; mark as seen to set `false`. Preserved when editing. |
| `external_links` | Map of labels to URL strings | Optional; defaults to `{}`. HTTP/HTTPS URLs only; shown as links opening in new tabs. Example: `{"Issue": "https://github.com/example/project/issues/1"}` |
| `metadata_map` | JSON object | Optional; defaults to `{}`; supports nested JSON values |

Seen state persists across restarts.

## API

| Method | Route | Result |
| --- | --- | --- |
| GET | `/api/notifications` | Paginated list, newest received first; optional `unread` filter |
| GET | `/api/notifications/{id}` | Get one |
| POST | `/api/notifications` | Create; returns 201 and Location header |
| PUT | `/api/notifications/{id}` | Replace editable fields; returns 200 |
| PATCH | `/api/notifications/{id}/seen` | Mark as seen; returns updated notification (safe to repeat) |
| DELETE | `/api/notifications/{id}` | Delete; returns 204 |

List parameters: `page` defaults to 0, `size` defaults to 20 (maximum 100), and
optional `unread=true`/`false` filters by seen state. The response contains
`items`, `page`, `size`, `totalElements`, and `totalPages`; clients previously
expecting an array must read `items`. UI search applies to the current page.

Invalid requests return 400; missing IDs return 404. PUT requires title and source; omitted description/metadata/external links reset to their defaults.

```sh
curl -i http://localhost:8080/api/notifications \
  -H 'Content-Type: application/json' \
  -d '{"title":"Build complete","description":"Ready to deploy","notification_source":"CI","metadata_map":{"branch":"main","build":42}}'
```

## Verify and package

Set `TEST_DATABASE_URL`, `TEST_DATABASE_USERNAME`, and `TEST_DATABASE_PASSWORD`
for a dedicated PostgreSQL test database. Integration tests delete rows in that
database. Running the packaged JAR uses the regular `DATABASE_*` settings.

```sh
./mvnw test
./mvnw package
java -jar target/windlass-0.0.1-SNAPSHOT.jar
```

Integration tests exercise the complete CRUD lifecycle, nested metadata, validation, missing resources, defaults, ordering, and static UI delivery using PostgreSQL.

## Deploy on another machine

To use the published `ghcr.io/rakorth/windlass:latest` image,
create a small bundle to hand out:

```sh
sh scripts/package-deployment.sh
```

Share `target/windlass-deployment.tar.gz`. The bundle includes the
[deployment instructions](deploy/README.md) and an environment template for
running the published image with Docker.

## Docker image

Copy `.env.example` to `.env` and fill in the PostgreSQL connection. To run an
image built from this checkout:

```sh
docker build -t windlass:local .
docker run -d --name windlass --restart unless-stopped \
  -p 127.0.0.1:6080:8080 --env-file .env \
  -v windlass-files:/data windlass:local
```

Open http://localhost:6080. PostgreSQL stores notifications, and the
`windlass-files` volume stores reference documents and JSON configuration.
See the [deployment guide](docs/deployment.md) for storage and port settings.

The [Docker image workflow](.github/workflows/docker.yml) builds on branch
pushes, pull requests, `v*` tags, and manual runs. Builds on the repository's
default branch and `v*` tags publish to `ghcr.io/<owner>/<repository>` using
GitHub's built-in `GITHUB_TOKEN`; other builds only validate the image.
Default-branch images include the `latest` tag, releases use their Git tag
(e.g. `v1.0.0`), and published images also include a `sha-<short-commit>` tag.
Image names are normalized to lowercase by the metadata action.

The workflow requests `packages: write`; repository/organization settings must
allow GitHub Actions to publish packages. Images are built and tested in parallel on native `linux/amd64` and
`linux/arm64` runners, then published together under the same multi-platform tags.
The application Dockerfile is separate from `.devcontainer/Dockerfile`.
