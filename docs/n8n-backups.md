# n8n backup and restore

Open **n8n backups** in the Windlass header, or visit `/backups.html`. The feature
is included in the Docker Compose setup:

```sh
docker compose up -d --build
```

## Download a backup

Choose **Download backup** when workflows are idle. Windlass gracefully stops
n8n, creates and validates a ZIP of its stored data, starts n8n again, waits for
readiness, and offers the download. Windlass remains available during this pause.

The ZIP includes the SQLite database, workflows, encrypted credentials, accounts,
settings, execution history, stored files, and the encryption key needed to
unlock credentials. Store the download securely outside the Docker host/dev
container. A backup contains both the encrypted credentials and their key.

Compose YAML, environment variables, external services, externally mounted files,
and Windlass's own notification database are not in the ZIP. Keep the project
configuration and n8n environment overrides separately. Backups apply to this
setup's local SQLite-backed n8n; they do not back up an external n8n instance or
PostgreSQL deployment.

## Restore a backup

1. Open **n8n backups** and choose a Windlass backup ZIP.
2. Check the confirmation acknowledging that the current n8n data will be replaced.
3. Choose **Restore backup** and keep the page open until the result appears.

Windlass validates the complete archive before stopping n8n: the ZIP structure,
paths, size limits, format/version metadata, encryption key, and SQLite integrity
must pass. The backup's n8n version must match the running version exactly. To
restore an older version, use a separate fresh instance configured for that
version; do not downgrade a newer live database in place.

Before replacing anything, Windlass creates a recovery ZIP of the current data.
It then installs the uploaded backup and starts n8n. If installation or startup
fails, it attempts to restore the recovery copy and start the original instance.
The page reports whether recovery succeeded. Restored active workflows may run
as soon as n8n starts. n8n account/password changes after the backup are also
reverted, so an existing n8n browser session may need to sign in again.

**Download recovery backup** retrieves the snapshot from before the last restore
attempt. Only the latest recovery copy is retained; a subsequent restore replaces
it. Download any recovery copy you want to keep before another restore.

Limits are 512 MiB per ZIP, 2 GiB expanded data, and 20,000 data entries. Safe
internal symbolic links are supported; chained links, external links, devices,
and other special files are rejected. Only ZIPs generated by this feature are
supported, not workflow JSON exports or the earlier manual `.tar.gz` archives.
The current instance must have an initialized, valid database so a recovery
snapshot can be created before restoring.

## Services and persistence

| Service | Responsibility |
| --- | --- |
| `windlass` | Serves the UI, requires deliberate same-origin backup requests, streams downloads and forwards uploads |
| `n8n` | Uses the official pinned n8n image with a small process supervisor; provides authenticated start/stop/status internally |
| `n8n-backup` | Archives and validates data, coordinates n8n's process, and retains the recovery ZIP |

The manager runs as UID/GID `1000`, the same as n8n, and mounts `n8n-data`.
Windlass does not mount that data volume and no service mounts the Docker socket.
The supervisor's port `5677` and manager's port `5680` are not published to the
host. Both require a generated bearer token for management requests.

The token is created in `n8n-control` with mode `0640`. Windlass joins group `1000`
and mounts that control volume read-only. The token is kept out of downloaded
backups and is never returned to the browser. n8n also mounts control read-only.
`n8n-backups` retains `recovery.zip` and any pending-restore marker. Both volumes
survive ordinary restarts and `docker compose down`; `down --volumes` deletes them.

On an interrupted backup, the manager starts n8n again. On an interrupted restore,
it reinstalls the saved recovery copy. A maintenance marker prevents n8n's
supervisor from starting the database prematurely after a container restart.
If recovery cannot finish, the marker and recovery ZIP stay in place. Inspect:

```sh
docker compose logs n8n-backup n8n
docker compose restart n8n-backup
```

Refresh status in the UI after restarting the manager. Do not remove the recovery
ZIP or maintenance markers to bypass a failed recovery. If a request times out,
check the current operation status before retrying; the server may still be
working.

Windlass remains a local application without user authentication. Its backup
endpoints have access to n8n credentials regardless of n8n's own login. Keep the
default loopback binding; an externally accessible deployment needs authentication
in front of Windlass. Same-origin request checks prevent browser form submissions
from other sites but do not replace user authentication.

## API

All routes are relative to Windlass. Downloads use `Cache-Control: no-store`.

| Method | Path | Result |
| --- | --- | --- |
| GET | `/api/automations/backups/status` | Availability, operation phase, n8n readiness/version, upload limit, recovery availability |
| POST | `/api/automations/backups` | Full ZIP download after n8n is ready again |
| POST | `/api/automations/backups/restore` | Multipart `file` plus `confirm=RESTORE`; restores and returns a result message |
| GET | `/api/automations/backups/recovery` | Latest recovery ZIP, or 404 if none exists |

Backup, restore, and recovery downloads require `X-Windlass-Backup: 1`.
Cross-site browser requests are rejected. Only one backup/restore/download
operation is allowed at once; competing requests return 409. Invalid ZIPs return
400, size-limit violations 413, version mismatches 409, and unavailable services
or failed recovery 503. Outside Compose, status reports the feature unavailable
unless `N8N_BACKUP_URL` and `N8N_BACKUP_TOKEN_FILE` are configured.

## Verification

These contributor checks run from a full source checkout, not the deployment bundle.

```sh
python3 -m unittest discover -s docker/n8n-backup -v
node --check docker/n8n/process.mjs
node --check src/main/resources/static/backups.js
docker compose build
```

The manager build runs its Python tests; the Windlass build runs its Java tests.
Tests cover archive round trips, path/link rejection, size/version checks,
database/key validation, rollback, interrupted-operation recovery, API guards,
file forwarding, downloads, and upstream failures. Runtime restore tests must use
a disposable Compose project with its own volumes, not live n8n data.
